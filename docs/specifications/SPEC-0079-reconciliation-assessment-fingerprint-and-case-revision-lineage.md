# SPEC-0079 - Reconciliation Assessment Fingerprint and Case Revision Lineage

Status: Accepted

Source decision: ADR-0079

## Objective

Define the exact content identity of a `FinancialReconciliationAssessment` and
the durable append-only binding between that assessment and the reconciliation
case revision produced from it.

The result must allow an independent downstream consumer to answer:

```text
Which exact governed assessment produced this case revision?
```

without reconstructing history from a lossy durable case or current financial
trace.

## Authorized design boundary

This specification defines:

1. assessment fingerprint canonicalization v1;
2. accepted-assessment fingerprint ownership;
3. exact assessment snapshot requirements;
4. case-revision lineage persistence semantics;
5. atomic commit requirements;
6. replay and concurrency behavior;
7. historical/legacy behavior;
8. integrity verification;
9. organization isolation;
10. downstream Decision Room consumption requirements.

This specification does not yet authorize implementation.

## Domain identity contract

Conceptually introduce:

```text
FinancialReconciliationAssessmentFingerprint
    canonicalizationVersion = 1
    sha256 = 64 lowercase hexadecimal characters
```

The digest algorithm for version 1 is SHA-256.

The fingerprint identifies complete assessment content.

It does not identify acceptance occurrence or case occurrence.

Byte-equal canonical version-1 representations MUST produce the same
fingerprint. SHA-256 is collision-resistant rather than injective, so equal
digests alone do not prove byte equality. If the same fingerprint is associated
with semantically different reconstructed snapshot content, the result is
`INTEGRITY_FAILURE`, never verified equality.

## Acceptance contract

`AcceptedFinancialReconciliationAssessment` remains the sole productive
assessment input into governed reconciliation case orchestration.

Acceptance owns fingerprint creation.

Conceptually:

```text
accept(
    assessment,
    acceptedAt
)
    -> AcceptedFinancialReconciliationAssessment(
           assessment,
           assessmentFingerprint,
           acceptedAt
       )
```

There is no public `fingerprint` parameter.

`acceptedAt` must retain the existing microsecond precision rule.

The fingerprint is computed before the value enters case processing.

## Canonicalization v1

### Encoding

Canonicalization v1 uses compact UTF-8 JSON generated by a dedicated domain
canonicalizer.

It must not use generic object serialization.

Rules:

- UTF-8;
- no BOM;
- no insignificant whitespace;
- no trailing newline;
- exact property order defined below;
- UUIDs use canonical lowercase hyphenated representation;
- arrays use only the frozen v1 ordering rules defined below;
- all money amounts are JSON strings, never JSON numbers;
- currency uses its canonical three-letter code.

Canonical JSON string escaping is frozen for v1: quote and backslash use JSON
backslash escapes; backspace, form feed, newline, carriage return and tab use
the standard short JSON escapes; every other U+0000 through U+001F code point
uses lowercase `\u00xx`; all other valid Unicode scalar values are emitted as
UTF-8 without optional escaping. The canonicalizer performs no Unicode
normalization and does not delegate byte identity to a generic serializer.

Canonical money text is frozen independently of future `MarketplaceMoney`
implementation changes:

```text
if numeric value == 0: "0"
else: value.stripTrailingZeros().toPlainString()
```

The result has no leading `+`, no exponent and no insignificant trailing
fraction zeros. Version 1 retains the current money-domain limits: absolute
value below `1000000000000000000` and at most six fractional digits.

The canonicalization version itself is part of the hashed representation.

### Top-level property order

The exact top-level order is:

```text
canonicalizationVersion
organizationId
traceId
orderId
currency
policyVersion
status
lines
```

The exact JSON value types are also part of v1:

- `canonicalizationVersion` is the JSON integer `1`;
- `organizationId`, `traceId` and `orderId` are canonical lowercase UUID JSON strings;
- `currency`, `policyVersion` and `status` are JSON strings;
- `lines` is a JSON array;
- there are no additional top-level properties.

A canonicalizer must therefore emit the same bytes regardless of any generic
serializer defaults for numeric/string coercion or unknown properties.

### Line order and property order

Canonicalization v1 does not use runtime enum ordinal as protocol identity.
Present lines are emitted according to this frozen v1 stage order:

```text
SALE
MARKETPLACE_COMMISSION
MARKETPLACE_FEE
SHIPPING
ADVERTISING
TAX
PRODUCT_COST
FINANCIAL_COST
OTHER_ADJUSTMENT
SETTLEMENT
PAYMENT_ACCOUNT
BANK
```

A future stage addition, removal or reorder must not silently alter v1. An
unknown stage fails closed under v1 and requires a new canonicalization version.
The frozen v1 reconciliation-status literals are `PENDING`,
`PARTIALLY_RECONCILED`, `DIVERGENCE` and `FULLY_RECONCILED`.

Each line uses this exact property order:

```text
stage
status
expected
actual
difference
```

### Reconciliation side representation

`FinancialReconciliationSide.NotObserved` is encoded as:

```json
{"kind":"NOT_OBSERVED"}
```

`FinancialReconciliationSide.Observed` uses the exact kind literal
`"OBSERVED"`.

The exact property order for `Observed` is:

```text
kind
netAmount
effectiveEntryIds
```

`effectiveEntryIds` is a JSON array of canonical lowercase UUID strings.

Money property order is always:

```text
currency
amount
```

`effectiveEntryIds` use frozen v1 unsigned-UUID ordering: compare the UUID
most-significant 64 bits as unsigned; if equal, compare the least-significant
64 bits as unsigned. This is independent of collection order and future runtime
comparator changes.

### Difference representation

`FinancialReconciliationDifference.NotComparable` is encoded as:

```json
{"kind":"NOT_COMPARABLE"}
```

`FinancialReconciliationDifference.Compared` uses the exact kind literal
`"COMPARED"`.

The exact property order for `Compared` is:

```text
kind
signedDifference
absoluteDifference
tolerance
```

Each money object uses:

```text
currency
amount
```

### Fingerprint calculation

The fingerprint is:

```text
lowercaseHex(
    SHA-256(
        canonicalAssessmentJsonUtf8Bytes
    )
)
```

The digest is always exactly 64 lowercase hexadecimal characters.

### Explicit exclusions

The following never enter canonicalization v1:

- acceptance time;
- case ID;
- case revision;
- case lifecycle status;
- opened/observed/resolved case timestamps;
- persistence timestamps;
- database row identity;
- HTTP representation;
- serializer metadata;
- Kotlin `hashCode()`;
- `toString()`;
- Decision Room projection fields.

## Snapshot contract

Lineage must store the complete governed assessment, not only its digest.

Snapshot schema version 1 has exactly these logical top-level fields:

```text
schemaVersion = 1
organizationId
traceId
orderId
currency
policyVersion
status
lines
```

Each line has exactly `stage`, `status`, `expected`, `actual`, `difference`.
A side is either `{"kind":"NOT_OBSERVED"}` or `OBSERVED` with `netAmount`
and `effectiveEntryIds`. A difference is either `{"kind":"NOT_COMPARABLE"}`
or `COMPARED` with `signedDifference`, `absoluteDifference` and `tolerance`.
Money objects contain exactly `currency` and canonical-v1 string `amount`.
Additional v1 snapshot fields are rejected.

Snapshot line arrays use the frozen v1 stage order and entry-ID arrays use the
frozen v1 unsigned-UUID order. JSONB object-property ordering is not identity,
but array ordering is part of snapshot v1.

`schemaVersion` inside snapshot v1 is the JSON integer `1`.

`assessment_snapshot_schema_version` is persistence metadata and is excluded
from the assessment fingerprint. The persisted metadata version and the embedded
snapshot `schemaVersion` must agree exactly; disagreement is
`INTEGRITY_FAILURE`.

Fingerprint canonicalization is performed from the reconstructed semantic
assessment under the stored fingerprint version.

Snapshot decoding and rehydration are owned by `marketplace-operations` beside
the reconciliation domain. Persistence must call a domain-owned validated
snapshot/factory boundary; it must not bypass internal assessment/line/side/
difference constructors or invent parallel reconciliation semantics.

On retrieval, the domain-owned decoder validates shape, versions, invariants and
canonical array order, reconstructs the governed assessment and recomputes the
fingerprint. Stored and recomputed digests must match before a result is
verified.

## Durable lineage model

The intended additive persistence concept is:

```text
marketplace_reconciliation_case_revision_assessment
```

Required logical fields:

```text
organization_id
case_id
case_revision
assessment_fingerprint_version
assessment_fingerprint
assessment_snapshot_schema_version
assessment_snapshot
accepted_at
```

Required logical key:

```text
PRIMARY KEY (
    organization_id,
    case_id,
    case_revision
)
```

The row must reference the organization-scoped durable reconciliation case.

`case_revision` is positive.

`accepted_at` has microsecond precision.

`assessment_fingerprint` is 64 lowercase hexadecimal characters.

No global uniqueness constraint is placed on assessment fingerprint within a
case.

## Append-only rule

A committed lineage row is immutable.

There is no application update or delete operation for lineage.

Database protection must reject direct update and delete attempts.

Idempotent replay is handled by comparison, not mutation.

## Atomic persistence contract

A case create/revision and its lineage row form one governed commit.

They must commit or roll back together.

The implementation must not perform independent case-save and lineage-save
transactions.

The application write boundary must expose one composite governed commit
operation carrying the candidate durable case and the exact accepted assessment,
fingerprint and snapshot together. The orchestrator must not coordinate two
independently committing repositories, and JDBC transaction state must not leak
into the application/domain contract.

For an existing case, this commit must serialize or compare-and-swap against the
organization-scoped current row, verify the expected revision and classify a
zero-row conditional write. Database constraints must make lineage-aware
current-revision/lineage consistency enforceable at commit time; application
call ordering alone is insufficient. Deferrable foreign keys, constraint
triggers or an equivalent PostgreSQL mechanism are acceptable if the required
semantics are proven directly.

Existing pre-lineage rows remain valid without fabricated lineage; historical
rows may remain unvalidated while the new invariant is enforced for newly
created or subsequently revised lineage-aware rows.

### Create

For a new case:

```text
case revision = 1
lineage revision = 1
```

Both rows commit atomically.

### Revision

For current case revision `N`, a changed accepted assessment creates exactly
`N + 1`.

The persistence layer must verify that the expected current revision is still
`N`.

Skipped revisions are invalid.

A stale writer must not overwrite a newer revision.

### Conditional-write result

A conditional update that affects zero rows is not success.

The persistence boundary must distinguish at least:

```text
APPLIED
ALREADY_APPLIED
CONFLICT
INTEGRITY_FAILURE
UNAVAILABLE
```

## Revision decision semantics

These rules run only after the existing eligibility gate accepts a `DIVERGENCE`
assessment. This specification does not make non-divergent assessments create,
revise or resolve durable cases.

Before any idempotence comparison, an existing current lineage row is verified
exactly as a governed read: supported versions, valid snapshot, recomputed
fingerprint, digest equality and case-context binding. A present-but-invalid
lineage is `INTEGRITY_FAILURE`; its stored fingerprint cannot be trusted as an
idempotence shortcut.

If current verified lineage exists:

```text
accepted fingerprint == current verified fingerprint
    -> UNCHANGED
    -> no new revision or lineage row
    -> acceptedAt is not rewritten

accepted fingerprint != current verified fingerprint
    -> create exactly N + 1
    -> insert exact lineage atomically
```

A changed non-divergent line inside an otherwise `DIVERGENCE` assessment still
advances revision even when the divergence-only durable projection is unchanged.
A fingerprint may recur after an intervening different assessment (A -> B -> A).

### Same revision replay

For an already committed `(organization, case, revision)`:

- same fingerprint and semantically identical reconstructed snapshot -> idempotent replay;
- different fingerprint -> integrity conflict;
- same fingerprint but different reconstructed semantic snapshot -> integrity failure.

## Legacy case behavior

Migration performs no historical lineage backfill.

Existing case revision `N` without lineage remains `LINEAGE_UNKNOWN`.

The first eligible accepted assessment after lineage activation must not be
bound retroactively to revision `N`.

Instead it creates revision `N + 1` with new verified lineage.

## Historical reconstruction prohibition

The system must never claim historical assessment identity by hashing or
reconstructing from:

- current durable case contents;
- current trace contents;
- current policy;
- evidence IDs retained by the case;
- newly recomputed reconciliation;
- current Decision Room projection.

## Lineage read contract

A governed lineage read is scoped by:

```text
organizationId
caseId
caseRevision
```

Possible semantics:

```text
FOUND_VERIFIED
NOT_FOUND
LINEAGE_UNAVAILABLE
INTEGRITY_FAILURE
```

A successful read must:

1. load the organization-scoped lineage row;
2. decode the supported snapshot version;
3. reconstruct the governed assessment snapshot/domain value;
4. recompute the fingerprint using the stored fingerprint version;
5. compare recomputed and stored fingerprints;
6. validate assessment organization/order/trace/policy/currency coordinates
   against the durable case;
7. return the assessment only if every verification succeeds.

Unsupported fingerprint or snapshot versions fail closed.

## Cross-organization isolation

All persistence keys and reads include `organization_id`.

A case or lineage belonging to another organization must never be returned as a
successful read.

Public consumers must not reveal whether a foreign case or lineage exists.

## Decision Room integration boundary

TASK-0165P does not modify TASK-0165O yet.

After lineage implementation is independently accepted, a subsequent
TASK-0165O integration may replace contextual-only assessment matching with a
source that consumes verified case-revision lineage.

The Decision Room must never:

- calculate the expected historical fingerprint from its own candidate;
- synthesize missing lineage;
- accept caller-declared assessment identity;
- reconstruct historical assessments from case stages;
- treat context equality as identity.

## Threat model and required adversarial tests

Implementation must prove at minimum:

1. same complete assessment -> same fingerprint;
2. changed non-divergent line in an otherwise divergent assessment changes fingerprint;
3. changed divergent line changes fingerprint;
4. permuted input lines produce the same v1 fingerprint;
5. permuted entry IDs produce the same fingerprint under frozen unsigned order;
6. a high-bit UUID vector proves unsigned rather than signed ordering;
7. acceptedAt does not change fingerprint;
8. case ID/revision/lifecycle metadata do not change fingerprint;
9. known-answer canonical bytes and SHA-256 are stable;
10. Kotlin runtime hashCode is irrelevant;
11. generic serializer formatting/property order is irrelevant;
12. v1 stage order does not derive from runtime enum ordinal;
13. unknown future stage fails closed under v1;
14. canonical money vectors prove zero/trailing-zero/negative/non-exponent behavior;
15. snapshot tampering is detected;
16. stored fingerprint tampering is detected;
17. unsupported canonicalization version fails closed;
18. unsupported snapshot version fails closed;
19. cross-organization read returns no foreign data;
20. current lineage is fully verified before unchanged/idempotent decision;
21. same current verified fingerprint is idempotent and does not rewrite acceptedAt;
22. different current verified fingerprint advances exactly one revision;
23. changed non-divergent line advances revision despite identical durable projection;
24. same revision + different fingerprint is conflict;
25. same fingerprint + different reconstructed semantic snapshot is integrity failure;
26. stale expected revision cannot overwrite;
27. revision skipping cannot commit;
28. lineage-aware case update without matching lineage cannot commit;
29. future lineage revision cannot commit while current case remains at another revision;
30. transaction failure rolls both writes back;
31. legacy case receives no synthetic lineage;
32. first eligible post-migration legacy observation creates N + 1 as first verified revision;
33. A -> B -> A across three revisions is allowed;
34. hostile transient source cannot self-attest identity to Decision Room;
35. persisted snapshot metadata version differing from embedded `schemaVersion`
    fails closed;
36. concurrent identical new-case attempts create one current case and one
    revision-1 lineage, with the loser classified as verified idempotent replay;
37. concurrent different assessments racing from the same current revision
    cannot both create `N + 1`, and the losing writer leaves no orphan lineage.

## Persistence migration constraints

The future migration is additive.

It does not rewrite existing financial ledger, Economic Truth or reconciliation
case history.

It creates no historical lineage rows.

The lineage table must enforce positive revisions/versions, lowercase 64-hex
fingerprint shape, JSON-object snapshot shape, organization-scoped case identity
and database rejection of lineage update/delete. For lineage-aware writes the
schema must also enforce that a current case revision cannot commit without its
matching lineage and that a newly inserted future lineage revision cannot commit
while the case remains at another revision. The implementation review must prove
these behaviors against PostgreSQL.

Rollback of application code does not delete lineage.

Destructive down migrations are prohibited.

## Non-goals

Not authorized by this specification:

- provider mutation;
- recovery execution;
- recommendation authority;
- causal attribution;
- a new reconciliation engine;
- a parallel truth store;
- a global assessment search API;
- automatic lineage backfill;
- a journal of every accepted occurrence;
- autonomous Decision Room action;
- rewriting TASK-0165O before this lineage is implemented and verified.

## Implementation gate

Implementation may begin only after ADR-0079 and SPEC-0079 survive design review.

The first implementation slice must start with canonical fingerprint
known-answer tests before introducing persistence.
