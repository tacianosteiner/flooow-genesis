# SPEC-0090 — Governed raw evidence reference (future contract)

Status: **design-only, non-executable**. Implements the decision in [ADR-0090](../adr/ADR-0090-governed-raw-evidence-reference.md) only after its future gate. This specification creates no endpoint, type, migration or implementation authority today.

## Identity and version semantics

`GovernedEconomicEvidenceReference` is a proposed **server-internal** immutable value, constructed only from a verified durable record and claim lineage:

| Field | Type / constraint | Meaning |
|---|---|---|
| `organizationId` | existing `OrganizationId` / UUID | Tenant boundary, from authenticated principal at retrieval; never trusted from UI. |
| `marketplaceOrderId` | existing `MarketplaceOrderId` / UUID | Durable economic evidence subject. |
| `observationId` | existing `MarketplaceEconomicEvidenceObservationId` / canonical lowercase UUID | Existing V015 identifier, never generated by the Room. |
| `evidenceVersion` | existing `MarketplaceEconomicEvidenceVersion` / positive 64-bit integer | Exact V015 update version linked by identifier FK; subject-level projection version alone is insufficient. |
| `identifierKind` | existing `FACT`, `ATTEMPT`, `CORRECTION` | Discriminator required for correct table interpretation. |
| `family` | existing `MarketplaceEconomicEvidenceFamily`, nullable only for an attempt/correction whose family cannot be established without replay | Observation family, verified from stored row; no guess from claim text. |
| `observedAt` | `Instant?`, microsecond precision | Fact/correction observation time when the stored row defines it; attempt uses its separate `attemptedAt`. |
| `sourceKind` / `sourceSystemKey` | existing `EconomicSourceKind?` / `EconomicSourceSystemKey?` | Server-side provider/source attribution where a fact has `EconomicSource`; never fabricated for attempts. |
| `sourceExternalReference` | existing `EconomicExternalReferenceState?`, **server-only** | Provider record reference when present. It is not assumed to be an occurrence ID and is not placed in a public URL or generic DTO. |

The existing observation ID is an internal evidence identity, **not** a provider occurrence identity. Some facts have `occurredAt` and a source external reference; collection attempts have `attemptedAt`; corrections have supersession links. A provider occurrence identifier or original provider document ID is `MISSING_CONTRACT` unless a source-specific durable contract proves it. A normalized V015 fact is durable evidence, but the existence of a retained raw provider document is unproven.

`ClaimEvidenceBinding` is a proposed separate immutable producer record, not a frontend join: claim kind (`SALES_ORDER_STATE`, `RECONCILIATION_CASE_REVISION`, or another separately governed enum), claim subject ID, organization ID, observation reference(s), exact source evidence version, `assemblyPolicyVersion`, optional `calculationPolicyVersion`, projection `lastAppliedChangeSequence`, and either `projectedAt` or exact reconciliation `caseId + revision + policyVersion`. Each binding must explain the observation's role (`SUPPORTS`, `CONTRADICTS`, `SUPERSEDED`, `ATTEMPT_ONLY`) and preserve correction lineage. This binding is **not currently persisted** for Sales Intelligence; its future storage and atomic producer semantics require a separately reviewed design/migration. A mere version match is not a binding.

## Invariants

1. Reference tuples must match one existing durable identifier row and its exact version/kind, under the same organization and order. A fact must also match its family row; corrections must preserve superseded and replacement identities.
2. Claim binding must be emitted by the server-side assembler/assessment from the exact evidence set used. No UI-generated, client-supplied or name/leaf-matched link is accepted.
3. A later evidence correction or projection update never rewrites a historical reference. The historical claim remains tied to its original version; the UI must show stale/superseded status separately.
4. An observed fact can support a claim without being canonical Economic Truth. Missing or conflicting evidence cannot be represented as zero or as an empty success list.
5. Financial ledger entry IDs, financial trace IDs, case IDs and V015 observation IDs are distinct namespaces. Crossing them requires an explicit, tested lineage contract.
6. Public representation excludes raw credentials, provider tokens, secret URLs, filesystem paths, unreviewed external references and sensitive payloads. No arbitrary URL is returned or followed.

## Availability and rendering

The current Room state is `RAW_EVIDENCE_REFERENCE=NOT_AVAILABLE`. Future retrieval should map outcomes to a bounded presentation vocabulary, while retaining the existing domain's `Found` / `NotFound` / `IntegrityFailure` semantics internally:

| Presentation state | Exact meaning |
|---|---|
| `AVAILABLE` | Exact binding and authorized redacted rendering verified against durable local evidence. |
| `NOT_EXPOSED` | Exact binding exists, but no approved render contract for this caller/class. |
| `REDACTED` | Record exists but fields or whole record are withheld by explicit policy. |
| `UNAVAILABLE` | Retrieval infrastructure unavailable; existence is not inferred. |
| `MISSING` | Authorized lookup found no matching durable record or historical revision. |
| `CONFLICTING` | Tuple, subject, revision, correction or claim context conflicts; no payload returned. |
| `NOT_AVAILABLE` | No exact claim-to-evidence binding exists. This is the present default and is not equivalent to `MISSING`. |

These are **proposed UI contract states**, not new canonical database statuses. A public response may collapse `MISSING` and cross-organization denial to one indistinguishable not-found status to prevent enumeration; internal audit retains the cause without leaking tenant existence. Rendering classes must be allowlisted per evidence family/kind, field-level redaction reviewed, payload size capped and pagination bounded. Availability never grants read permission by itself.

## Retrieval contract — design only

No existing OpenAPI route returns V015 observations. A future route belongs under the existing authenticated Sales Intelligence read surface, with a **server-selected binding token or scoped claim reference**, not a free-form evidence URL or arbitrary observation ID lookup. Exact route syntax is deferred until the producer binding and persistence review. The handler must derive organization from service bearer context, verify claim/order/revision binding, read only local durable evidence, validate the full tuple, enforce rendering class, limit response and return no provider content by live fetch. No provider call on Room page load. Errors are non-mutating and indistinguishable where needed to prevent ID enumeration.

For a Sales Intelligence `UNRESOLVED` claim, the approved chain would be Decision Pressure → loaded order and exact projection context → assembler's recorded observation/attempt/correction bindings → V015 identifier/version and fact rows → authorized redacted rendering. For an open reconciliation claim, it would be case ID + case revision + trace/policy → explicit assessment/ledger lineage → independently proven economic observation bridge, if one exists. Current `evidenceEntryIds` alone stop at ledger entries.

## Adversarial cases and acceptance gates

Negative tests must cover foreign organization, guessed ID, valid ID on wrong order, wrong version/kind/family, stale projection, corrected/superseded fact, missing historical row, unresolved attempt, case/order mismatch, forged frontend ID, unauthorized rendering, sensitive source reference, oversized payload, external URL injection and provider-call amplification. Positive tests require exact provenance, historical revision retention, authorized redacted fields and stable claim linkage under concurrent updates. Audit should record safe categories without raw payload or secrets.

Implementation is blocked until canonical producer linkage, persistence/atomicity design, retrieval security, redaction policy and tests are independently approved. `ROOM_OPERATIONAL` remains false and execution/recovery authority remains blocked.
