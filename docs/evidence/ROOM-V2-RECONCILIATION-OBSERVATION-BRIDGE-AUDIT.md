# Room V2 — reconciliation to economic observation bridge audit

Date: 2026-10-12. Status: **PARTIAL_BRIDGE**; raw-evidence retrieval remains blocked. This corrects the overly broad inference that no ledger-to-observation bridge exists: [V032](../../applications/marketplace-operations-persistence-postgres/src/main/resources/db/migration/V032__create_financial_ledger_materialization_lineage.sql) supplies one for the governed materialization subset.

## Verified path and limits

The [materialization boundary](../../applications/marketplace-operations/src/main/kotlin/io/flooow/marketplace/operations/economics/ledger/materialization/MaterializationBoundary.kt) accepts a concrete `MarketplaceEconomicComponentObservation`, checks organization/order/currency, source authority identity, semantic version and source fingerprint, and emits a verified plan. Its [commit contract](../../applications/marketplace-operations/src/main/kotlin/io/flooow/marketplace/operations/economics/ledger/materialization/MaterializationCommit.kt) requires one atomic durable commit of trace, ledger entry and source-to-entry lineage. V032 records `(organization_id, source_order_id, source_authority_identity)` and a unique `(organization_id, ledger_entry_id)`, with FKs to the V015 component fact, ledger entry and trace. Its insert trigger compares stage, basis, amount, direction, source fields and occurred time; update/delete triggers make lineage immutable. Correcting ledger entries are explicitly rejected by this B3-B1 boundary.

The [reconciliation case](../../applications/marketplace-operations/src/main/kotlin/io/flooow/marketplace/operations/economics/reconciliation/DurableReconciliationCase.kt) retains `FinancialLedgerEntryId` values and stage-level expected/actual entry IDs, case revision and trace. The [case API](../../applications/marketplace-operations-api/src/main/kotlin/io/flooow/marketplace/api/ReconciliationCasesApi.kt) exposes those ledger IDs, not observation IDs. A **server-side** scoped join can therefore prove a path for an entry that actually has a matching V032 lineage row: case/org/trace/order → case evidence entry ID → ledger entry → V032 lineage → V015 component fact/identifier. The V015 observation's own evidence version and kind must still be checked. No client-side string conversion or assumed UUID equivalence is valid.

No source evidence proves that *every* reconciliation entry was created through B3-B1, that all historical case revisions retain an immutable exact entry set for Room retrieval, or that a case's entire divergence can be reduced to the materialized subset. V032 is component-fact only; attempts, order occurrence, external identity, corrections and ledger entries from other authorized paths are outside its proven bridge. The [Decision Room projection](../../applications/marketplace-operations/src/main/kotlin/io/flooow/marketplace/operations/economics/reconciliation/EconomicDecisionRoomProjection.kt) formats string references but does not expose a verified typed observation join. Its authority-source SQL consults V032 for some context; that does not establish a general raw-evidence read route.

## Future bounded read contract

Given authenticated organization, server-resolved case ID and exact case revision, load the stored case entry set and trace/order. For each entry, verify same organization, trace and order; left-join V032 under all keys. Classify `BRIDGED_COMPONENT_FACT`, `UNBRIDGED_LEDGER_ENTRY`, `CONFLICTING_LINEAGE` or `UNAVAILABLE` without guessing an observation. For a bridged entry, verify V015 fact/identifier version and correction state; apply redaction before a bounded response. The complete case must not be labeled raw-evidence-complete while any entry is unbridged or case revision unavailable. Cross-tenant and guessed IDs must be indistinguishable externally. This is design only; no endpoint or migration is authorized here.
