## Lifecycle findings

ClientAuthentication_hook receives the authentication result before AuthenticationOk. Native authenticated/session role establishment happens afterward. MyDatabaseId is finalized still later, after database locking/revalidation. PGPROC membership and initial status already exist at authentication. Thus self pidfd acquisition is possible in the running process, but native final role/database identity is not available there. Looking up the requested role/database name is not the same as proving final session identity. Runtime hook/socket capability was not tested. [auth.c](https://raw.githubusercontent.com/postgres/postgres/REL_18_4/src/backend/libpq/auth.c), [auth.h](https://raw.githubusercontent.com/postgres/postgres/REL_18_4/src/include/libpq/auth.h).

Raw-source sequence: InitProcessPhase2 → pgstat_beinit/initial → authentication → InitializeSessionUserId → finalize MyDatabaseId → startup settings → session preload → pgstat_bestart_final → initialization commit → login event → client command loop/ReadyForQuery. Session preload has valid native identity, but final external activity role/database publication follows it. A receiver waiting for those final SQL-visible fields while the preloader waits for ACCEPT can time out or deadlock. No premature status-publication patch was adopted. [postinit.c](https://raw.githubusercontent.com/postgres/postgres/REL_18_4/src/backend/utils/init/postinit.c).

Shared preload is postmaster-start loading, not a general after-auth callback. A module must register an actual later lifecycle path. `_PG_init` is not rerun simply because an already-loaded shared library is listed again in session preload. Session preload is superuser-controlled; local preload is user-controlled and cannot enforce mandatory admission. Current preload settings are all empty and parameter ACLs are empty. [miscinit.c](https://raw.githubusercontent.com/postgres/postgres/REL_18_4/src/backend/utils/init/miscinit.c), [dfmgr.c](https://raw.githubusercontent.com/postgres/postgres/REL_18_4/src/backend/utils/fmgr/dfmgr.c), [GUC contexts](https://raw.githubusercontent.com/postgres/postgres/REL_18_4/src/backend/utils/misc/guc_tables.c).

ExecutorStart covers planned execution, not BEGIN/SET and other utility-only work. ProcessUtility is a distinct dispatch. Combining first-command hooks does not move enrollment before connection admission; an idle authenticated connection can exist before either callback. Reject executor-only/first-query admission for the required complete lifecycle. [executor.h](https://raw.githubusercontent.com/postgres/postgres/REL_18_4/src/include/executor/executor.h), [execMain.c](https://raw.githubusercontent.com/postgres/postgres/REL_18_4/src/backend/executor/execMain.c), [utility.c](https://raw.githubusercontent.com/postgres/postgres/REL_18_4/src/backend/tcop/utility.c).

PostgresMain calls EventTriggerOnLogin after InitPostgres returns and before its client command loop. The login event runs functions in a transaction using fmgr dispatch; ordinary clients do not need an explicit enrollment SELECT. Administrative installation is required. The proposed private native event handler would accept zero SQL identity arguments, require login-event call context and an ordinary client backend, and use authenticated/session IDs rather than effective SECURITY DEFINER identity. Failure would explicitly raise FATAL before admission. [postgres.c](https://raw.githubusercontent.com/postgres/postgres/REL_18_4/src/backend/tcop/postgres.c), [event_trigger.c](https://raw.githubusercontent.com/postgres/postgres/REL_18_4/src/backend/commands/event_trigger.c).

The event must be ADMIN-owned, enabled ALWAYS, protected against DROP/ALTER, with `event_triggers` enabled and no service privilege to change it or session_replication_role. Handler direct EXECUTE must be revoked from PUBLIC and services; its identity logic must use GetAuthenticatedUserId and GetSessionUserId even if private execution uses an existing trusted owner. These are release requirements, not installed objects or claimed runtime guarantees. No new service grant is intrinsically required by this direction. Native dependency/ABI review remains required.

## Canonical role, slot and incarnation

ADR0090 states one login has one permanent binding/slot, including tombstones. SPEC0090 sections 3/4 define exact OID/name matching and canonical identity_slots bytes: purpose 1 VERIFIER, 2 ISSUER, 3 EXECUTOR, 4 AUDITOR. V043 offline_binding_header stores identity_slots, deployment_id and deployment_incarnation_id in the immutable header. The lookup key is authenticated OID plus exact role name against validated canonical slot records; the result must be unique and agree with the binding fingerprint. Role names alone, enum order in Kotlin and policy duration values are not allocation authority.

SLOT_BINDING_SOURCE=immutable header identity_slots; MUTABILITY=immutable assignment/permanent no-rebinding, with live catalog revalidation; AUTHORITY=SERVICE_IDENTITY_ADMIN allocation and PLAN_BINDING_ADMIN immutable binding governance. Existing mutable role catalogs prove current attributes, not the slot allocation itself.

Incarnation authority is the same immutable header's deployment/incarnation tuple, matched to protected offline_readiness and independently approved host deployment/incarnation evidence under the existing clone/reincarnation contract. Readiness is keyed by incarnation_id. Header assignment is immutable; readiness is ADMIN-controlled and mutable; normal restart retains incarnation, explicit reincarnation invalidates copied bindings. A caller UUID, a single readiness row or system_identifier alone is insufficient.

Fresh read-only disposable evidence established `binding_header_count=0`, no binding rows, readiness NOT_READY and watchdog_healthy=false. Four existing governed-named logins have catalog identities, but **no current canonical slot assignments were obtained**. The current validated enrollment caller set is empty. This is missing bound evidence/contract at this baseline, not a claim that V043 has no canonical representation. No new header, table, policy, role map or host-manifest authority was invented.

The unresolved connection-admission contract must define how a role is recognized as requiring governed enrollment when its header is absent, without treating it as unmanaged by default and without broadening enforcement to unrelated normal-runtime roles. It must bind the exact rehearsal/deployment OID/name roster to the approved host incarnation through existing authority, or explicitly govern a new authority source. Inferring the four slots from `g3f4_*` names is forbidden. No implicit provisioning authorization is created here.

## Application and connection lifetime

GovernedSources obtains a slot DataSource Connection inside `.use`, configures autocommit/isolation/read-only, and then enters governed work. Current PostgresDataSources constructs PGSimpleDataSource, so launcher acquisition is a new physical connection; it is not a pooling implementation. Distinct DataSources prevent cross-slot reuse, but neither class enforces one concurrent connection per slot.

A native self-enrollment call could be inserted before configuration/work and discard the connection on failure, but it is absent today and would add EXECUTE authority. Driver startup/session configuration may occur before the adapter gets Connection; an application call cannot prove universal server admission or protect bypassing clients. No application code was changed. Prefer the automatic login event direction over this additional service surface. One enrollment per physical backend is required; multiple simultaneous live anchors per slot must remain representable unless a canonical concurrency policy forbids them.

## Generation, handshake and digest requirements

PgStartTime backs pg_postmaster_start_time; PostmasterPid and system_identifier are metadata. Timestamp/PID reuse and cloned system_identifier forbid using these alone as a strict process-generation fence. Old backend pidfds remain dead after exit and cannot address new backends. A surviving receiver must invalidate its entire server context on loss/death of the authenticated control connection/anchor, require fresh generation confirmation after restart, and accept only new live descriptors. The exact nonpersistent startup/receiver epoch bootstrap and namespace topology remain design requirements, not a tested restart protocol. [timestamp.c](https://raw.githubusercontent.com/postgres/postgres/REL_18_4/src/backend/utils/adt/timestamp.c), [timestamp.h](https://raw.githubusercontent.com/postgres/postgres/REL_18_4/src/include/utils/timestamp.h).

Required admission protocol is synchronous: server-native handler derives self identity and transfers its self pidfd; receiver compares supplied/kernel-message/kernel-peer anchors, obtains fresh READ COMMITTED canonical binding evidence, checks liveness again, and returns ACCEPT with receiver-issued enrollment ID and identity digest, or typed DENY. The backend completes admission only after exact ACCEPT agreement. Missing receiver, malformed response, expired deadline, missing/ambiguous binding, stale incarnation, wrong role/database or dead anchor must FATAL-close the governed connection. No fire-and-forget or PID fallback. Receiver endpoint identity and private mount/PID-namespace expectations must be pinned; privileged host/DB administration remains trusted.

A production protocol ceiling and finite acknowledgment deadline must come from an explicitly governed existing authority/derivation. No new timing number or substitute policy meaning was selected. Therefore the handshake remains **specified as obligations, not a closed executable contract**. No prototype is authorized until the binding, admission deadline and complete entrypoint contract close.

Proposed non-secret digest framing follows existing tagged canonical-encoding conventions with a new explicit domain: `FLOOOW/OFFLINE-WATCHDOG/ENROLLMENT/V1`; u32be domain length, domain bytes, u16be field count, ascending u16be tags and u32be lengths. Fixed proposed fields are protocol version u32, database OID u32, authenticated role OID u32, exact role-name UTF8, slot-purpose u8, backend PID u32, backend-start instant i64, postmaster-start instant i64, binding UUID, deployment UUID, incarnation UUID and receiver/server-epoch correlation bytes. UUIDs are 16 network-order bytes; instants are microseconds with checked epoch conversion. No keys/passwords/cancel secret or raw fd number is included. PIDFD is the retained live anchor, not serialized authority. Receiver-derived slot/incarnation must come from protected server state. Epoch representation/provenance and canonical frame limits remain unresolved; this encoding is a review draft, not a new frozen Package0090 codec.

Replay/duplicates: fresh receiver-issued connection context, one bounded exchange, accepted ID scoped to the retained anchor and current server/incarnation; payload alone cannot reauthorize. Duplicate descriptors proven to reference the same live process and same canonical metadata are equivalent/idempotent, close redundant descriptors. Different process anchors sharing a slot are distinct enrollments, never overwrite each other; concurrency must follow an existing proven policy. Unknown policy cannot mean one connection per slot. Incarnation/recovery supersession invalidates prior enrollments. Primary deregistration is pidfd readability/death, not a client SQL cleanup call. These policies were designed, not implemented/tested in this gate.
