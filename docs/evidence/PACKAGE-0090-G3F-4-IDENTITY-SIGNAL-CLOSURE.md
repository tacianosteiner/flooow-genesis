## Required property and scope

Authorization identifies deployment UUID, incarnation UUID, database OID, governed slot, role OID, PID, backend start timestamp, current postmaster generation, client-backend type, and a kernel process-instance anchor. The last field is required but currently unbound. An implementation must atomically act on that same process instance or return `TARGET_CHANGED_OR_GONE_NO_SIGNAL`. Equality of descriptive database fields alone cannot establish that the opened kernel handle belongs to the authorized backend.

Application name is diagnostic labeling, not authority. Targets must exclude the postmaster, auxiliary processes, autovacuum, workers, foreign databases, unmanaged roles, superusers and the watchdog itself. Exact governed role/slot and deployment/incarnation evidence must precede action. No populated canonical binding header was established by this review; the existing rehearsal identity record is not promoted into a new production binding authority.

## PostgreSQL 18.4 lifecycle and native mechanisms

All PostgreSQL source files were byte-verified against `REL_18_4`; hashes and raw-source line anchors are recorded in the JSON inventory. Line numbers below refer to downloaded raw bytes, not browser-rendered line numbering.

Startup registration order is ProcKill, then RemoveProcFromArray in InitProcessPhase2, then pgstat_beshutdown_hook in pgstat_beinit. The exit callback stack runs in reverse order: invalidate backend status, remove ProcArray membership, release PGPROC, then process exit. MyStartTimestamp is descriptive PostgreSQL startup time, not a kernel-issued process-generation handle. [postinit.c, InitPostgres](https://raw.githubusercontent.com/postgres/postgres/REL_18_4/src/backend/utils/init/postinit.c).

`InitProcess` assigns a reusable PGPROC slot and writes its PID. Ordinary shutdown invokes shared-memory callbacks; ProcArray removal precedes `ProcKill`, which clears PID and returns the slot to the free list, with lock-group deferral where applicable. ProcStructLock protects allocation/free-list updates, not kernel lifetime. Its spinlock is private implementation state; holding it across a system call is not a supported process-lifetime fence. No new lock order was installed. [proc.c, allocation and ProcKill](https://raw.githubusercontent.com/postgres/postgres/REL_18_4/src/backend/storage/lmgr/proc.c).

ProcNumber identifies a currently occupied slot and can be reused; it is not a durable backend-generation identifier. BackendId is not an additional independent generation fence for this PG18 interface. [procnumber.h](https://raw.githubusercontent.com/postgres/postgres/REL_18_4/src/include/storage/procnumber.h).

Backend status is indexed by ProcNumber. Its PID and `backend_start` derive from MyProcPid and MyStartTimestamp. The shutdown hook marks the status entry invalid. Change counters provide coherent copies, not kernel process ownership; local backend-status copies may be cached, so a second SQL observation is not necessarily fresh. [backend_status.c, pgstat_bestart_initial, pgstat_beshutdown_hook and pgstat_read_current_status](https://raw.githubusercontent.com/postgres/postgres/REL_18_4/src/backend/utils/activity/backend_status.c).

`BackendPidGetProc` releases ProcArrayLock before returning. The locked variant protects the array entry while held. Neither a PostgreSQL LWLock nor a spinlock can prevent an abnormal kernel process exit. Holding ProcArrayLock can delay cooperative removal; it does not prove that an abruptly dead process cannot be reaped and its number reused. Candidate A is **UNSAFE as a universal kernel-lifetime fence**, with private-API fragility as an additional limitation. [procarray.c, BackendPidGetProc and BackendPidGetProcWithLock](https://raw.githubusercontent.com/postgres/postgres/REL_18_4/src/backend/storage/ipc/procarray.c).

The postmaster reaps with `waitpid` before dispatching backend cleanup. Failed clean detachment triggers crash handling and termination of remaining children. That later cleanup is not an atomic fence around another process's kernel-handle acquisition. Thus abnormal-exit metadata must not be treated as a live-process certificate. [postmaster.c, child reaping, CleanupBackend and HandleChildCrash](https://raw.githubusercontent.com/postgres/postgres/REL_18_4/src/backend/postmaster/postmaster.c).

`pg_signal_backend` resolves and authorizes a PGPROC, then calls numeric PID/process-group `kill`. The source explicitly discusses reuse between those steps. Adding external database predicates does not alter that action path: **PID_ONLY_NATIVE_SIGNAL_STRICT_IDENTITY_SAFE=NO**. [signalfuncs.c](https://raw.githubusercontent.com/postgres/postgres/REL_18_4/src/backend/storage/ipc/signalfuncs.c).

Cancel-key validation releases its spinlock before numeric PID/process-group SIGINT. The source also recognizes this race. Extracting cancel keys would introduce secret authority and still leave the final action race. The cancel protocol supplies no corresponding termination capability. Candidate C: **CANCEL=NOT_VIABLE; TERMINATE=NOT_VIABLE** for this strict contract. No key was extracted. [procsignal.c, SendCancelRequest](https://raw.githubusercontent.com/postgres/postgres/REL_18_4/src/backend/storage/ipc/procsignal.c).

## Race timelines

Ordinary exit: A is observed → shared-memory callbacks invalidate status/remove ProcArray membership/free PGPROC → A exits → parent reaps A → OS may assign the number to B → numeric action may reach B. A genuinely fresh post-open status check can reject ordinary turnover; it cannot turn a later numeric `kill` into an instance-bound action. [ipc.c, proc_exit and shmem_exit](https://raw.githubusercontent.com/postgres/postgres/REL_18_4/src/backend/storage/ipc/ipc.c).

Abnormal exit: A is observed → abrupt death bypasses cooperative PostgreSQL cleanup → parent/kernel reaps A → numeric PID becomes reusable → B obtains it → pidfd_open resolves B while an A-shaped shared-memory entry may remain → database recheck may still report A → an unanchored pidfd action could reach B. This is an admissible source-derived counterexample to the proposed observe/open/re-read sequence; it was **not** reproduced as a wrong-process delivery. The counterexample does not assume that B was enrolled as a managed backend: rejecting unrelated kernel processes is part of the required scope.

Post-open exit: an fd already referencing A retains that kernel object and does not retarget to B. This closes the later redirection race but not the earlier acquisition/binding race.

## Linux pidfd and platform review

`pidfd_open` resolves the numeric PID at open time. `pidfd_send_signal` resolves the pid object from the fd and uses that object for delivery. Holding an fd does not keep a process alive or reserve the numeric PID. This establishes stable handle targeting after acquisition, not correspondence to earlier PostgreSQL metadata. The evaluated unanchored sequence is **PIDFD_IDENTITY_SIGNAL=UNSAFE**; a stronger anchored design remains unproved. [Linux v6.18 pid.c](https://raw.githubusercontent.com/torvalds/linux/v6.18/kernel/pid.c), [Linux v6.18 signal.c](https://raw.githubusercontent.com/torvalds/linux/v6.18/kernel/signal.c).

The basic syscall floor is Linux 5.3 for open and 5.1 for send. Permission follows normal signal checks; the tested caller and backend both used OS UID 999 in the same container PID namespace. No additional capability or seccomp adjustment was requested. Syscalls were invoked directly through the image libc `syscall`, not inferred from libc wrapper availability. Availability must be checked on every deployment; there is no numeric-kill fallback. [pidfd_open manual](https://man7.org/linux/man-pages/man2/pidfd_open.2.html), [pidfd_send_signal manual](https://man7.org/linux/man-pages/man2/pidfd_send_signal.2.html).

The actual runtime was kernel `6.18.33.2-microsoft-standard-WSL2`, x86_64, PostgreSQL `180004`, pinned image `sha256:07fc165de5bb569d822460e2df645c5489f99220fc2cb16c86596d39db394561`, gcc `14.2.0`, seccomp mode 2. Linux v6.18 source establishes upstream API behavior; it is not a claim of byte identity to Microsoft's kernel build. Three real governed executor sessions each produced successful pidfd_open, signal-0 permission probes and exit readability polling. No SIGINT or SIGTERM was sent. Immediately after exit readability, signal 0 still returned success; ESRCH was **not observed**, and successful syscall return is not an observed cancellation/termination outcome.

PIDFD_GET_INFO also worked and returned parent PID 1. This identifies parentage, not the authorized backend generation. Modern pidfs permits process-handle comparison through inode identity on 64-bit kernels, but a token obtained only after opening B has no independently enrolled A token to compare. A possible future self-enrollment/handle-registration design needs its own proof of enrollment provenance, postmaster epochs, registry lifetime, abnormal cleanup, slot rebinding and exact incarnation authorization. It has not passed this gate. [Linux v6.18 pidfs.c and PIDFD_GET_INFO](https://raw.githubusercontent.com/torvalds/linux/v6.18/fs/pidfs.c), [pidfd UAPI](https://raw.githubusercontent.com/torvalds/linux/v6.18/include/uapi/linux/pidfd.h).

Candidate D provides no additional proven Linux mechanism here. `kill`, process-group IDs and `/proc` lookups retain numeric resolution or observation races; ptrace/process freezing would add authority and cannot be assumed safe. No Windows PostgreSQL requirement was introduced.

## Authority, failures and gate disposition

No mechanism was selected, so no executable SQL signature, extension registration or fully specified new authority contract is asserted. A future proven primitive belongs in a separate `offline_watchdog_control` module; the crypto ABI remains untouched. It would use private ADMIN-only access and closed CANCEL/SIGINT versus TERMINATE/SIGTERM actions, with fixed search_path if SQL-exposed. This is a required boundary, not an installed capability. New service/database privileges, PUBLIC or service EXECUTE grants, arbitrary signal numbers and arbitrary process selectors were not introduced.

Required typed failures for a future primitive are: ESRCH → TARGET_GONE_NO_SIGNAL; EPERM → DENY_PERMISSION_NO_SIGNAL; EINVAL → DENY_INVALID_REQUEST_NO_SIGNAL; ENOSYS/unavailable pidfd → DENY_UNSUPPORTED_NO_SIGNAL; missing/mismatched backend, role, database, incarnation or process anchor → TARGET_CHANGED_OR_GONE_NO_SIGNAL; successful send without observed effect → SIGNAL_SENT_OUTCOME_UNCONFIRMED; bounded termination expiry → TERMINATION_TIMEOUT; lost DB/unknown authority → DENY_AUTHORITY_UNAVAILABLE_NO_SIGNAL. These are design requirements; no unimplemented behavior is reported as tested. No implicit success and no PID fallback are permitted.
